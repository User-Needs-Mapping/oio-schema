# OIO — the Outside-in Org data model

OIO is an interchange format for describing an organisation from the outside in: who its
users are, what they are trying to accomplish, what the organisation must be able to do,
what systems and teams make that possible — and, optionally, the investigation and
reasoning going on around all of that.

A document is YAML (or JSON), validated by a JSON Schema in [schemas/](schemas/). It is
meant to be written by a facilitator, generated by an AI-assisted interview, exported by a
tool, read by a different tool, and reviewed by a human in a pull request. Everything in
the format is shaped by that last requirement.

## What problem it solves

Two tools that both model an organisation can usually exchange the *structure* — a list of
teams, a list of capabilities, the edges between them. What they cannot usually exchange is
the investigation: what someone observed, whether anyone checked it, what might be limiting
the available choices, what change in conditions is being pursued, what decision is on the
table and which alternatives were weighed.

The workaround is to write all of that into node descriptions. That keeps the words and
loses everything that makes them usable. Once flattened into prose:

- a report from one person and a corroborated finding look identical;
- a suspected explanation and a confirmed constraint look identical;
- a proposal and a committed decision look identical;
- nobody can tell which entity an observation was actually about;
- the alternatives that were considered and rejected are gone;
- and a decision's record of what it was taken under quietly updates itself whenever
  someone edits the description.

OIO 1.1 gives those things typed homes, so an importing tool can preserve the difference
rather than having to guess at it.

### What it is not

OIO is not an enterprise ontology, not a replacement for the systems that hold the real
data, and not a requirement to gather everything before anyone is allowed to discuss a
decision. A model with three capabilities and one signal is a legitimate OIO document. Most
models should stay structural-only; reach for the investigation extension when there is an
investigation to carry.

A schema's `$id` is an identifier for the contract, not a URL to fetch it from. Consumers
strip or ignore it and resolve internal `$ref`s against the in-memory document.

## The structural model and the extension

An OIO document has two layers.

**The structural core** — `users`, `needs`, `capabilities`, `technical_systems`, `teams`,
`org_groups`, `data_assets`, `external_dependencies`. This is OIO 1.0, and it is unchanged.
A document that uses only these sections needs no version declaration and no identifiers.

**The investigation extension** — `metrics`, `signals`, `constraints`, `outcomes`,
`flow_decision_records`. Added in OIO 1.1. A document that uses any of these must declare
`system.oio_version: "1.1"`, so a consumer can tell before it starts reading whether it can
read the document at all.

### Entities

| Entity | Section | What it is | Required fields |
|---|---|---|---|
| System | `system` | The boundary being modelled | `name` |
| User | `users` | A person or external system that has needs | `name` |
| Need | `needs` | What a user is trying to accomplish | `name`, `user` |
| Capability | `capabilities` | Something the organisation must be able to do | `name` |
| Technical system | `technical_systems` | A concrete implementation enabling capabilities | `name` |
| Team | `teams` | A unit that stewards capabilities and systems | `name`, `type` |
| Team interaction | `teams[].interacts` | How two teams work together | `with`, `mode` |
| Org group | `org_groups` | A grouping of teams | `name` |
| Data asset | `data_assets` | Shared storage or messaging revealing implicit coupling | `name`, `type`, `description` |
| External dependency | `external_dependencies` | A system outside the boundary | `name`, `description` |
| Metric | `metrics` | A named, reusable measure | `id`, `name` |
| Signal | `signals` | An observation or report that warrants attention | `id`, `name` |
| Constraint | `constraints` | A condition limiting the available choices | `id`, `statement` |
| Outcome | `outcomes` | A desired change in conditions for identifiable beneficiaries | `id`, `name` |
| Flow decision record | `flow_decision_records` | A decision being considered or made | `id`, `title` |
| Check-in | `outcomes[].check_ins`, `flow_decision_records[].check_ins` | A dated observation about one of them | `id`, `at` |
| Decision option | `flow_decision_records[].options` | One course of action considered | `id`, `summary` |

Teams are classified with the **Team Topologies** pattern language. `capability.evolution_stage`
is **Wardley evolution** — how ubiquitous and certain a practice is in the wider world. It is
not internal effectiveness, not implementation maturity, and not retirement status.

### Relationships

Every relationship is declared on its source, following the existing OIO convention that one
end is the source of truth.

**Structural** (references resolve by *name*):

| Relationship | Declared on | Valid targets |
|---|---|---|
| has need | `needs[].user` | user |
| fulfilled by | `needs[].fulfilledBy` | capability |
| decomposes into | `needs[].decomposesInto` | need |
| depends on | `capabilities[].dependsOn` | capability |
| decomposes into | `capabilities[].decomposesInto` | capability |
| enables | `technical_systems[].enables` | capability |
| constrains | `technical_systems[].constrains` | capability |
| depends on | `technical_systems[].dependsOn` | technical system |
| depends on external | `technical_systems[].externalDeps` | external dependency |
| stewards | `teams[].stewards` | capability, technical system |
| interacts with | `teams[].interacts[].with` | team |
| contains | `org_groups[].contains` | team, capability |
| used by | `data_assets[].usedBy` | technical system |

**Investigation** (references resolve by *id*):

| Relationship | Declared on | Valid targets | Carries |
|---|---|---|---|
| references | `signals[]`, `constraints[]`, `outcomes[]` | any structural entity, team interaction, or identified relationship | `note` |
| cites | `flow_decision_records[].cites` | signal | `note` |
| reveals | `signals[].reveals` | constraint | `effect: revealed · confirmed · contradicted` |
| impedes | `signals[].impedes` | flow decision record | `encountered_at` |
| bounds | `constraints[].bounds` | flow decision record, outcome | `state_at_commit: assumed · confirmed` |
| serves | `flow_decision_records[].serves` | one outcome | `note` |
| affects | `flow_decision_records[].affects` | user, need, capability, team, external dependency | `role: context · subject · affected` |
| requires | `flow_decision_records[].requires` | flow decision record | `note` |
| beneficiaries | `outcomes[].beneficiaries` | user, team, org group | `note` |
| supersedes | any investigation record | a record of the same kind | |

Four kinds of link are kept apart on purpose, and no generic "related to" edge exists:

- **Structural dependency** — `dependsOn`, `enables`. One thing needs another to work.
- **Evidential support** — `cites`, `reveals`, `references`. One record is evidence about another.
- **Intended effect** — `serves`, `affects`, `bounds`. Someone means to change something.
- **Temporal sequence** — `supersedes`, `impedes`, and the dates on records. One thing came
  after another.

`requires` orders decisions against each other. It is not a process flow, and the dependency
graph is not a sequence diagram.

## A small structural example

```yaml
system:
  name: Payments platform

users:
  - name: Customer

needs:
  - name: Get money back quickly
    user: Customer
    outcome: When I am owed a refund, I see it without having to chase it.
    fulfilledBy:
      - Refund Processing

capabilities:
  - name: Refund Processing
    visibility: user-facing
    strategic_importance: core

teams:
  - name: Payments
    type: stream-aligned
    stewards:
      - Refund Processing
```

Full validated fixture: [`examples/structural-only.oio.yaml`](examples/structural-only.oio.yaml).

## A small extended example

```yaml
system:
  name: Payments platform
  oio_version: "1.1"

users:
  - id: usr-customer
    name: Customer

capabilities:
  - id: cap-refunds
    name: Refund Processing

signals:
  - id: sig-refund-delay
    name: Refunds taking days to reach customers
    signal_type: dependency
    severity: concern
    evidence: reported
    observed_at: 2026-03
    provenance:
      source: Support team lead
      source_type: interview
      recorded_at: "2026-04-02"
      note: One source. Not corroborated with finance or with customers.
    references:
      - target: cap-refunds
        entity_type: capability
    reveals:
      - target: con-batch-window
        effect: revealed

constraints:
  - id: con-batch-window
    statement: Refunds settle only in the overnight banking window
    certainty: assumed
    standing: live
    bounds:
      # No state_at_commit: the decision below has not committed, so there is no
      # belief-at-commitment to record. See "Identity, references and renaming".
      - target: fdr-refund-speed

outcomes:
  - id: out-refunds-feel-immediate
    name: A customer sees their refund without having to chase it
    status: draft
    beneficiaries:
      - target: usr-customer
        entity_type: user
    success_criteria:
      - Support stops fielding "where is my refund" contacts.

flow_decision_records:
  - id: fdr-refund-speed
    title: How should refunds reach customers faster?
    question: What is actually holding a refund up, and what would move it?
    status: draft
    options:
      - id: opt-intraday
        summary: Move refunds to intraday settlement
      - id: opt-notify-earlier
        summary: Tell the customer the refund is on its way when it is raised
    cites:
      - target: sig-refund-delay
    serves:
      target: out-refunds-feel-immediate
```

Nothing above claims more than it knows. The signal is `reported` by one person. The
constraint is `assumed`. The decision is `draft` with two options and no chosen one. Full
validated fixtures:

- [`examples/investigation-unvalidated.oio.yaml`](examples/investigation-unvalidated.oio.yaml)
  — a discovery conversation with a single informant. Nothing in it has been validated with
  anyone else, and it is written to stay that way.
- [`examples/decision-and-review.oio.yaml`](examples/decision-and-review.oio.yaml) — a
  clearly fictional worked example of a decision that was committed, enacted, watched and
  reviewed, including a constraint whose state has changed since.

## How the five investigation concepts differ

They are easy to blur, and blurring them is the failure mode this format exists to prevent.

**A Signal is something someone noticed.** It is not proof of a cause and not proof of a
defect. Three independent axes, and collapsing any two of them loses information:

- `signal_type` — the *nature* of the tension: `dependency`, `cognitive-load`,
  `ownership-gap`, `unmet-need`, `structural-tension`, `other`.
- `severity` — how much *attention* it warrants: `info`, `concern`, `critical`.
- `evidence` — how well *supported* the claim is: `reported`, `corroborated`,
  `direct-observation`, `measured`, `disputed`.

`evidence` is **not a ranked scale** — these are distinct epistemic states, not rungs — and
it has **no default**. An unknown evidence status is recorded by leaving the field out. A
reported concern can be `critical` and uncorroborated at the same time; that combination is
normal and important, not a contradiction.

Provenance is separate again, and every field of it is optional: `source`, `source_type`,
`recorded_at`, `recorded_by`, `note`. **When something was reported is not when it
happened** — `provenance.recorded_at` is the first, `observed_at` and `observation_window`
are the second. Dates accept a year, a month or a day, so a vaguely known date is recorded
vaguely rather than padded into a false precision.

**A Constraint is a condition that limits the available choices.** Two independent axes:

- `certainty` — has anyone actually checked? `assumed` or `confirmed`.
- `standing` — does it still bite? `live`, `accepted` or `lifted`.

They move independently. A constraint can be assumed and lifted, or confirmed and live. A
suspected explanation for a signal is `assumed` until someone checks it; a signal `reveals`
a constraint, and revealing one does not confirm it.

`bounds[].state_at_commit` records the constraint's certainty at the moment the decision it
bounds was **committed**, and is deliberately allowed to disagree with the certainty the
constraint carries today. Two rules follow, and both matter:

- A decision still in `draft` has no moment of commitment, so it cannot carry a stamp.
  Recording one asserts a belief nobody ever held, and is rejected.
- On a committed decision, an **absent** stamp is a fact rather than a gap — it means the
  condition was named *after* the decision was made. It is never filled in from the
  constraint's present certainty.

**A Constraint is not an impediment.** A constraint is a persisting condition. A single
obstruction met while enacting a decision is a *signal* that `impedes` that decision, and it
may or may not have a standing condition behind it. There is no Impediment entity, and a
signal that impedes a decision keeps its own `signal_type`, so the same signal can obstruct
one decision and be cited as evidence by another.

**An Outcome is a desired change in conditions for identifiable beneficiaries.** It is not a
user need, not a capability, not a delivered artefact, not a project milestone, and not a
decision's verdict. It carries intent (`description`), who is meant to be better off
(`beneficiaries`), and how anyone would know (`success_criteria`, in plain language).
`measures`, `target_date` and numbers are all optional, and an outcome is fully
representable before any of them are settled.

**A Flow Decision Record is a decision being considered or made.** Four separate axes:

- `status` — where it stands as a decision: `draft`, `committed`, `observing`, `reviewed`.
- `phase` — where it sits on a roadmap: `proposed`, `now`, `next`, `later`.
- `rollout_status` — how far enactment actually got: `not-yet`, `partial`, `rolled-out`.
- `verdict` — what a review concluded: `supported`, `not-supported`, `inconclusive`.

A `draft` record implies no approval, no commitment and no enactment. It may carry `options`
and no `decision` text at all — that is the honest representation of an open question.
`decision` becomes required once `status` leaves `draft`; `verdict` becomes required once
`status` is `reviewed`.

**A check-in is a dated observation about an outcome or a decision**, kept with the record it
is about rather than as a separate node. It is fully usable with no measurement at all:
`note` alone is a valid check-in. Where readings exist they name a defined metric and can
carry the `context` a later reader would need to compare them fairly. Three things stay
separate: `note` is what was observed, `interpretation` is what the recorder took it to mean,
and a decision's `verdict` is a judgement about the decision — never stored on the check-in.

### User needs are not Outcomes

A **need** is what a user is already trying to accomplish. It is true of them now, whether or
not anyone does anything. An **outcome** is a change in conditions somebody intends to bring
about, for beneficiaries who can be named.

`need.outcome` is a **first-person sentence** about what success looks like for that user
("I can see my booking is confirmed before I set off"). It is not, and must never be
reinterpreted as, a reference to an entry in the `outcomes` section. Its meaning is unchanged
from OIO 1.0 and legacy documents are unaffected.

### An FDR's verdict is not an Outcome

The review conclusion on a decision is called `verdict`, never "outcome". They answer
different questions:

- **Verdict** — *was this a good bet, given what we then knew?*
- **Outcome** — *has the condition we were pursuing actually changed?*

A decision can be judged `supported` while the outcome it serves is still `observing`, and
that combination is common. The `decision-and-review` fixture shows exactly it.

## Identity, references and renaming

The structural core resolves references **by name**. That works, and it means an entity's
name is load-bearing: rename a capability and every `fulfilledBy` pointing at the old name
stops resolving.

The investigation extension resolves references **by id**, so evidence and decisions stay
attached through a rename.

| | |
|---|---|
| Syntax | `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$` |
| Uniqueness | Across the **whole document**, every identified record, not per section |
| Where required | Every investigation record, metric, check-in and decision option |
| Where optional | Every structural entity, the long form of a relationship, and a team interaction |
| Missing target | Error — `unresolved-reference` |
| Wrong kind of target | Error — `target-type-not-allowed` |
| Duplicate id | Error — `duplicate-id`; never resolved to whichever came first |
| Ambiguous name | Error — `ambiguous-name`; never resolved to the first match |

An investigation record can only reference a structural entity that has an `id`. Adding one
is the whole migration, and only where evidence is actually being attached — there is no
requirement to identify a model wholesale.

A signal can also point at a **team interaction** or at a **relationship**, not only at
entities, by giving that interaction or that long-form relationship an `id`. The
`decision-and-review` fixture does both: the tension it records lives in the handover, not
inside either team.

### What is not supported: edge-level uncertainty

OIO 1.1 has **no way to mark a structural relationship as a hypothesis**, and offers no
substitute. `relationship.role`, fulfilment degree and dependency strength keep their
structural meanings, and must never be repurposed to encode confidence — a `supporting` role
says what part a link plays, not how sure anyone is that it exists. No confidence number is
introduced either, because there is no basis on which to produce one.

Where a structural link is uncertain, record a **signal** with an `evidence` status that
references the entities involved, and say so in its provenance note. If the edge is declared
in long form, give it an `id` and have the signal reference the edge itself. The
`investigation-unvalidated` fixture does the former for two needs attributed to executives by
a single informant, and says so in a comment.

## Validating

```
npm install
npm test
node scripts/validate.mjs examples/structural-only.oio.yaml
```

The validator does two things: JSON Schema validation, then the cross-reference checks JSON
Schema cannot express — identifier uniqueness, reference resolution and allowed target types.

```
node scripts/validate.mjs [--schema 1.0|1.1] [--json] [--strict] <file...>
```

| Flag | Effect |
|---|---|
| `--schema` | Validate against a specific version (default `1.1`) |
| `--json` | Machine-readable results on stdout |
| `--strict` | Treat warnings as failures |

Findings go to stderr and JSON results to stdout, so it composes. Exit codes: `0` clean, `1`
validation failed, `2` could not run.

```
npm run validate:examples
node scripts/validate.mjs --schema 1.0 examples/structural-only.oio.yaml
node scripts/validate.mjs --json examples/decision-and-review.oio.yaml
```

`npm test` runs the schema checks and the document behaviour tests, and validates every
complete YAML example in this README.

### Continuous integration

[`.github/workflows/ci.yml`](.github/workflows/ci.yml) runs on every push and every pull
request. It installs with `npm ci` — which fails outright if `package-lock.json` has drifted
from `package.json` — then runs the tests, validates the examples through the CLI, and
validates the structural example against the frozen 1.0 contract.

It runs on Node 20, 22 and 24 on Linux, plus Node 22 on Windows. The matrix is not
decoration: `node --test` changed how it resolves path and glob arguments between Node 20
and 22, and the examples are authored on Windows while CI runs on Linux. The minimum
supported version is declared as `engines.node: ">=20"`.

### Checking the shared vocabulary

OIO's enum vocabularies are deliberately aligned with Fast Flow Toolkit, the application these
documents are exchanged with, so that interchange is a mapping rather than a translation. That
ontology evolves on its own schedule, and OIO has already been caught out once: the decision
verdict values changed while OIO 1.1 was being written, and nothing noticed until a person
happened to look.

```
npm run check:ontology -- <path-to-the-consumer-schema-profile>
```

It compares all 18 shared vocabularies — signal type, severity and dismiss reason; constraint
certainty and standing; outcome status and archived reason; the four decision-record axes;
intervention type, confidence and reversibility; metric direction; and the `reveals`, `bounds`
and `affects` link properties — and exits non-zero on any disagreement. Add `--json` for
machine-readable output.

The check runs where both artefacts are to hand: locally, or in the consuming application's
own pipeline. The latter is where a vocabulary change actually originates, so that is where the
signal arrives soonest — inside the change itself, rather than days afterwards.

It is one-directional by design. It reports where OIO disagrees with the consumer; it does not
decide which is right, and changes nothing automatically. OIO follows the consuming
application's agreed ontology rather than negotiating with it, so a disagreement is a prompt
to go and read the decision behind it.

## Versions, compatibility and migration

`system.oio_version` declares the contract a document was written against. It is **required
whenever any investigation section is present**, and the schema enforces that.

Be precise about what compatibility does and does not mean here:

| Claim | True? |
|---|---|
| An existing structural document stays valid under the current schema | **Yes** — tested |
| An existing structural document stays valid under the frozen 1.0 contract | **Yes** — tested |
| A 1.1 document can be read by a validator that only has the 1.0 schema | **No** |
| Optional new sections make old validators forward-compatible | **No** |

The top level is closed with `additionalProperties: false`. Adding sections in 1.1 does not
make an old validator able to read them — it makes it refuse the whole document. That is
tested, so the README cannot drift into claiming otherwise.

**Version selection.** [`schemas/versions/oio-schema-1.0.0.json`](schemas/versions/oio-schema-1.0.0.json)
is the frozen structural contract, kept so a consumer can select it explicitly rather than
inferring it. It differs from the schema previously committed here in its `$id`, its
description, and two corrected field descriptions — no property, type, enum or `required`
change.

**Migrating a structural document to 1.1.** Nothing is required. Add `system.oio_version:
"1.1"` and identifiers only when you start attaching investigation records — and only to the
entities you actually reference.

**Unsupported content.** A consumer must **declare or report** what it does not implement.
Silently dropping the investigation and importing the structure is precisely the failure this
extension exists to prevent. `unsupportedSections(doc, supported)` in
[`scripts/lib/validate-oio.mjs`](scripts/lib/validate-oio.mjs) returns the list to report.

**Structural-only projection is explicitly lossy.** `projectToStructural(doc)` returns the
projected document *and* an account of what was dropped — each investigation section with its
record count. Projecting all the way back to 1.0 (`{ target: "1.0" }`) additionally strips
identifiers, and reports how many, because the 1.0 contract has no room for them.

**Presentation stays out.** Frames, canvas positions, colours, layout and interface settings
have no place in the shared semantic core, and there is no field in which to declare them.
A producer with its own presentation concerns keeps them in its own files.

The JSON Schema dialect stays **draft-07**. Nothing here needs a later one.

## Consumer support

Fast Flow Toolkit is the application OIO was built to exchange with. OIO is an interchange
format, so it is worth being precise about what actually exists.

**Schema availability, converter support and application support are three separate facts.**
This repository provides the first. It does not provide the other two, and publishing a schema
does not make any tool able to read it.

**No released application imports an OIO 1.1 investigation document today.** The structural
core has a working consumer; the investigation extension does not yet. If you are planning
around that, ask for current status rather than inferring it from this repository.

The vocabularies OIO shares with that application are listed under
[Checking the shared vocabulary](#checking-the-shared-vocabulary), and
`npm run check:ontology` verifies them against a given profile.

Nothing in this repository is an application round-trip test. The tests here validate schemas
and documents — that is all they establish, and none of them should be described as more.

## Guidance for AI-generated documents

An interview-style agent will produce most of the investigation content this format carries.
The format can hold uncertainty, but only if the author declines to resolve it.

**Do:**

- Mark every unverified claim. One person's account is `evidence: reported`. A suspected
  explanation is a constraint with `certainty: assumed`.
- Preserve what was actually said, in the source's own words where you can, in `description`.
  Put your reading of it somewhere else — a check-in `interpretation`, an FDR `rationale`.
- Leave unknowns out. There is no field in this schema that must be filled. An absent
  `recorded_at`, `source`, `evidence`, measure or target means *unknown*, and that is a
  supported state.
- Record alternatives, including the ones nobody liked, in `options`.
- Use the level of attribution that was agreed. A role is often right where a name is not.

**Do not:**

- Invent a team, an org structure, a reporting line or a decision-making authority that
  nobody described.
- Invent dates, metrics, baselines or targets. A target nobody agreed is not a placeholder,
  it is a fabrication that later reads as a commitment.
- Invent customer needs, or attribute a need to a user who has not been asked. If an informant
  attributes a need to someone else, record the attribution as a signal and say who attributed
  it.
- Turn a proposal into a decision. No `chosen_option` and no `decision` text unless someone
  actually chose.
- Turn a report into a finding by citing it. Citing a signal from a decision does not upgrade
  its `evidence`.
- **Read absence as evidence of absence.** A missing stewardship link means stewardship is
  *unknown*, not that nobody stewards it. A customer connection missing from a supplied map is
  evidence about the map, not about the organisation.

## Contributing

Changes to a schema are changes to a contract other tools depend on. In a pull request:

- Run `npm test` and `npm run validate:examples`. CI runs both on every push and pull
  request across Node 20, 22 and 24, so a green local run on one version is not the whole
  story.
- Say which of the two schema files changed, and whether the change is additive or breaking.
  Adding a required field, removing a property, or narrowing an enum breaks existing
  documents.
- Do not edit `schemas/versions/oio-schema-1.0.0.json` for anything other than a documentation
  correction. It is frozen.
- Update the examples and this README alongside the schema. The tests check that the README's
  examples still validate, so a stale README fails the build.
- Record a material semantic decision in [`docs/decisions/`](docs/decisions/), alongside
  [0001](docs/decisions/0001-investigation-and-decision-extension.md).
- If you change a vocabulary shared with FFTK, cite the FFTK decision record that changed it,
  and run `npm run check:ontology` against a local checkout.
- Do not edit [`LICENSE`](LICENSE). It is the official Apache 2.0 text and a test pins its
  digest. Licensing notes belong in [`LICENSING.md`](LICENSING.md) or this README.

### What the licence would and would not cover

Once applied, Apache 2.0 would cover **this repository's material**: the schemas, the
validation tooling, the tests, the examples and the documentation.

It would **not** reach a model you write. Creating, validating or exchanging an `.oio.yaml`
document that conforms to OIO does not oblige you to license your own model or your
organisational data under Apache 2.0, and does not make them a derivative work. A schema
describes a shape; conforming to a shape is not copying the description of it.

The one boundary worth knowing: text copied out of [`examples/`](examples/) into your own
document is this repository's material, and the licence would apply to what you copied. Your
own content stays yours.
